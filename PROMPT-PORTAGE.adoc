ultracode — Utilisez un workflow multi-agents pour porter NOALYSS en Crystal. Taille de workflow libre : lancez autant d'agents que nécessaire.

## Mission

Le projet s'appelle *Partiduo* (portage de NOALYSS, AGPL-3.0-or-later, dépôts `aloli-crystal/partiduo-*`). Porter le cœur de NOALYSS, `/Users/philippe/prod-github/noalyss/noalyss-app/` (PHP), en Crystal dans `/Users/philippe/prod-crystal/partiduo/partiduo-app/`.

La spécification est dans `/Users/philippe/prod-crystal/partiduo/partiduo-docs/` : `CARTOGRAPHIE-NOALYSS.adoc` et `adr/ADR-001` à `adr/ADR-006`. Je les considère validés. En particulier :
- ADR-006 (modules activables) : `partiduo-app` = un *socle* toujours actif + des *modules* activables par instance — Comptabilité, Facturation, Analytique, Stock. Aucun module n'appelle un autre module : ils communiquent par le socle et les événements. La CI exécute les specs dans trois configurations (Comptabilité seule, Facturation seule, les deux). Le module Facturation suit ADR-006 D5 (numérotation attribuée à la validation, sans trou, facture intangible, avoir de type 381, mentions obligatoires générées, PDF/A-3 Factur-X).
- ADR-003 (contrat d'extension) : le cœur doit accueillir les extensions dès le lot 0 — registre et manifeste, routes `/ext/<code>/`, permissions déclaratives, événements, API publique documentée. Aucune extension n'est portée dans cette exécution, mais créez `partiduo-skel` (ADR-003 D8) pour prouver que le contrat fonctionne.
- ADR-005 (interface interchangeable) : `partiduo-app` ne contient *aucun* handler, gabarit ni fichier statique ; il expose le contrat `Partiduo::Api` (commandes, requêtes, objets de vue). L'interface est un dépôt séparé, `prod-crystal/partiduo/partiduo-ui-bulma`, qui ne dépend que de `Partiduo::Api`. Mettez en place dès le lot P le garde-fou CI de l'ADR-005 D3. L'apparence et l'ergonomie suivent la maquette de référence : `partiduo-docs/maquette/index.html`.
- ADR-004 D5 : les champs de facturation française (SIREN, SIRET, identifiant de routage, catégorie d'opération, TVA sur les débits, adresse de livraison) et l'événement `payment.matched` appartiennent au cœur. Prévoyez-les dans les lots 1 et 2.

Les extensions amont (`prod-github/noalyss/<projet>`) peuvent être lues pour comprendre ce que le cœur doit leur exposer. Toute la documentation produite est en AsciiDoc (`.adoc`), en français.

## Autonomie totale

- Ne me posez aucune question. Pour toute ambiguïté, choisissez l'option la plus simple et réversible, consignez-la dans `partiduo-app/DECISIONS.adoc` (contexte, choix, alternative écartée), et continuez.
- Ne vous arrêtez pas sur un blocage : contournez-le, notez-le dans `partiduo-app/BLOCAGES.adoc`, passez au lot suivant.
- Autorisé : créer `partiduo-app/`, `partiduo-ui-bulma/`, `partiduo-skel/` et `partiduo-migrate/` dans `prod-crystal/partiduo/`, `git init` avec une branche `development` (si le bac à sable refuse l'écriture de `.git/config`, faites le `git init` dans `$TMPDIR` puis déplacez le dépôt), commiter (commits conventionnels, par lot, sans ligne Co-Authored-By), installer des shards, créer des bases PostgreSQL locales préfixées `partiduo_` (dev/test uniquement), corriger un bug avéré dans les shards `prod-crystal/webauthn` et `prod-crystal/totp` (commit dans leur dépôt, noté dans DECISIONS).
- Interdit : pousser vers un dépôt distant, modifier quoi que ce soit dans `prod-github/noalyss/`, modifier les ADR (proposez plutôt un amendement dans DECISIONS), toucher à d'autres bases que `partiduo_*`, modifier d'autres shards de `prod-crystal/` que ceux cités.
- PostgreSQL est joignable uniquement par socket Unix (`/tmp/.s.PGSQL.5432`), pas en TCP : utilisez `psql` sans `-h`, et des URL de connexion de la forme `postgres:///partiduo_dev?host=/tmp`.
- Si PostgreSQL est injoignable, écrivez quand même le code et les specs, notez-le dans BLOCAGES, et continuez.

## Arbitrages (questions ouvertes des ADR)

1. Version amont : figée sur `rel10200-7-g4bd46a13f`.
2. Nom : `partiduo-app` ; licence AGPL-3.0-or-later (œuvre dérivée de NOALYSS, GPL-2.0-or-later). Chaque dépôt `partiduo-*` contient le texte intégral de l'AGPL v3 dans `LICENSE`, `license: AGPL-3.0-or-later` dans `shard.yml`, et un README qui cite NOALYSS et son auteur ; chaque fichier source commence par l'en-tête SPDX `# SPDX-License-Identifier: AGPL-3.0-or-later`.
3. Factur-X, CII et connexion à une Plateforme Agréée : traités par l'extension `partiduo-einvoicing` (ADR-004), portée dans une exécution ultérieure. Hors périmètre ici, sauf les champs et l'événement cités plus haut.
4. CAPTCHA : abandonné. En contrepartie, le lot 0 *doit* limiter les attaques en ligne (temporisation croissante après échecs, et blocage du compte après 10 échecs avec mécanisme de déblocage) : c'est la condition du palier CNIL à 50 bits (délibération 2022-100) appliqué par `prod-crystal/password-policy` ; sans ce mécanisme, il faudrait 80 bits.
5. Lot 6 (stocks, prévisions, suivi) : reporté, après tout le reste. La GED devient l'extension `partiduo-document` (ADR-003).
6. Auth : passkey + TOTP + mot de passe local ; SAML intégré via `prod-crystal/saml` ; OIDC en interface pluggable (implémentation après le noyau). Codes de récupération par défaut. Comptes comptables nominatifs. Instances en sous-domaines `<dossier>.partiduo.local`, `rp.id` = `partiduo.local`. Jetons machine : hors périmètre. TOTP : compatible avec n'importe quelle application d'authentification, sans en recommander ni en nommer aucune ; paramètres par défaut de la RFC 6238 uniquement (SHA-1, 6 chiffres, 30 s), QR code et secret base32 affichés. Aucun utilisateur n'est jamais repris : `partiduo-migrate` ne migre ni les utilisateurs ni leurs secrets TOTP. `TOTP::Authenticator#verify` renvoie un compteur : le stocker (`last_otp_counter`) et le repasser en `after:`, sinon un code reste rejouable.
7. TVA : BE et FR, isolées dans `vat/be/` et `vat/fr/`.

## Ordre et parallélisation

Plan de lots de l'ADR-001 : P → 0 → 1 → (2 et F en parallèle) → M → 3 → 4 → 5 → 6. Partiduo démarre de zéro (aucune donnée à reprendre), mais l'outil de reprise `partiduo-migrate` est obligatoire (ADR-001 D5) : c'est un *dépôt séparé*, `prod-crystal/partiduo/partiduo-migrate`, qui dépend de `partiduo-app` comme shard et n'écrit que par ses services publics ; source FEC d'abord, base NOALYSS ensuite.
- Un agent « architecte » pose le squelette et les conventions partagées ; rien d'autre ne démarre avant que le squelette compile.
- Ensuite, parallélisez par application Marten (`core`, `accounting`, `cards`, `vat`, `analytic`, `reporting`…) en respectant les dépendances de modèles.
- Pour chaque lot : un agent implémente, un agent `ruby-crystal-tester` écrit les specs, un agent `ruby-crystal-reviewer` relit ; corrigez ses remarques avant le commit.
- Chaque agent lit le code PHP et le SQL d'origine correspondant (`prod-github/noalyss/noalyss-app/`) pour reproduire les règles métier, pas seulement les écrans.

## Définition de « terminé » pour chaque lot

- `crystal tool format src/ spec/` puis `crystal spec` : 100 % vert.
- `marten migrate` passe sur une base vierge.
- Contraintes d'intégrité comptable en base (écriture déséquilibrée refusée par PostgreSQL), testées.
- Commit du lot.

## Jalon minimal exigé à la fin

P + 0 + 1 fonctionnels : `bin/partiduo-provision` crée une instance vierge avec le plan comptable de son régime (FR ou BE), on s'y enrôle, on crée et consulte plan comptable, fiches, exercices et journaux. `partiduo-skel` s'active sur l'instance, affiche sa page sous `/ext/SKEL/` pour un profil autorisé, la refuse aux autres, et reçoit l'événement `entry.posted`. Continuez ensuite aussi loin que possible, en visant le second jalon 2 + M : saisie des écritures, puis `partiduo-migrate` importe un FEC (générez-en un de démonstration, par exemple depuis une base NOALYSS créée avec les scripts SQL de `noalyss-app/`) avec un rapport de réconciliation juste au centime. Troisième jalon, F : sur une instance « Facturation seule » puis « Comptabilité + Facturation », un devis transformé en facture validée (numéro attribué, PDF/A-3 Factur-X valide selon `pdf-validate`), puis payée ; avec la Comptabilité, l'écriture de vente est générée et lettrée.
